# EdgeDoctor-RT：让设备在停机前开口

> 运行在 PSoC Edge E84 上的离线工业设备智能诊断终端。它把设备振动转化为故障类型、健康度、报警和可追溯日志。

## 一台机器真正停下来之前

旋转设备很少毫无征兆地停机。

轴承开始磨损、转子出现不平衡、轴系逐渐偏离中心时，机器通常还在转。最先改变的不是产线状态，而是振动。变化藏在连续波形里，幅度可能很小，频率成分却已经发生偏移。靠人巡检，这些信号容易错过；把原始数据持续送往云端，又会受到网络、时延和数据边界的限制。

EdgeDoctor-RT 想解决的就是这段空白：在机器仍然运转时，把诊断放到设备旁边。

它运行在 Infineon PSoC Edge E84 Edgi-Talk 开发板上，以 RT-Thread 管理实时任务。设备振动进入板端后，系统按固定节奏完成窗口更新、频谱特征提取和故障分类，再把结果变成操作员能直接读懂的健康度、故障概率和报警记录。整个过程不依赖云端，也不需要从 SD 卡加载模型。

这不是把一个分类器搬进 MCU。真正要做的是让数据、模型、运行时、界面和日志在同一块板上持续工作，而且不能互相拖慢。

## 项目做成了什么

EdgeDoctor-RT 已经打通下面这条链路：

```text
KAIST 旋转机械振动记录
        ↓
数据校验与记录级划分
        ↓
25.6 kHz → 6.4 kHz 重采样
        ↓
1 秒滑动窗口与 64 维频带特征
        ↓
64–32–5 轻量 MLP
        ↓
Q7 权重量化并编译进固件
        ↓
RT-Thread 板端回放、DSP 与推理
        ↓
健康度、五类概率、报警、CSV 日志与时延统计
```

最终输出五种设备状态：

| 类别 | 现场含义 |
|---|---|
| 正常 | 当前振动模式未显示四类目标故障 |
| 轴承内圈故障 | 内圈相关振动特征占主导 |
| 轴承外圈故障 | 外圈相关振动特征占主导 |
| 不对中 | 轴系对中状态异常 |
| 不平衡 | 转子质量分布异常 |

模型给出分类结果，HMI 再把结果翻译成健康度、置信度、异常评分和报警状态。操作员不需要阅读原始频谱，也能知道“现在是否异常、可能是什么故障、置信度多高、是否已经确认处理”。

## 数据先过关，成绩才有意义

项目使用 KAIST Human Lab 发布的旋转机械数据集 v6。当前振动训练集包含 45 条原始记录，覆盖五类状态和 0 Nm、2 Nm、4 Nm 三种负载。每条记录均匀抽取 40 个一秒窗口，共得到 1800 个样本窗口。

真正关键的不是窗口数量，而是怎么划分。

同一条长记录切出的相邻窗口高度相似。如果先切窗，再随机分配训练集和测试集，同一段运行过程很可能同时出现在两边。模型看似取得高分，实际只是认出了熟悉的记录。EdgeDoctor-RT 在切窗之前按完整记录划分：1400 个窗口用于训练，200 个用于验证，200 个用于测试。测试集里的记录不会以另一段窗口的形式混进训练集。

![KAIST 数据类别与负载分布](../artifacts/training/kaist-vibration-v1/dataset_distribution.png)

项目还做了按负载留一验证（LOLO）。每次拿掉一种负载，只用另外两种负载训练，再看模型面对未见工况时还能保留多少能力。这个测试比普通随机划分更接近现场：设备换了负载，振动分布也会跟着变。

### 没有硬凑“声振融合”

仓库最值得保留的一条记录，不是某个高分，而是一次主动停手。

KAIST v6 的声学压缩包只有五条零负载记录。进一步核对 Test.Lab 元数据后发现，同名声学文件和振动文件的绝对采集时间也不一致。它们代表相同工况，却不是同一时刻采到的同步信号。

如果只按文件名拼接，项目可以很快得到一份“多模态”结果，但那个结果没有可信的时间对应关系。EdgeDoctor-RT 没有绕过校验器，也没有把两段不同时间的数据伪装成同步样本。当前正式精度只来自振动通道。系统接口和 HMI 保留了音频通道，为以后接入真实同步声振数据做准备，但板载分类函数目前不使用音频输入。

这条边界必须在比赛现场说清楚：声振融合是产品方向，不是当前成绩。

## 一秒振动，怎样变成五个概率

原始振动采样率是 25.6 kHz。进入算法链后，信号重采样到 6.4 kHz，以 20 ms 为一个数据块。50 个数据块组成一秒分析窗口；窗口每前进 25 个块，也就是每 0.5 秒产生一次新诊断。

```text
20 ms 数据块 × 50
        ↓
1 秒分析窗口
        ↓ 每 25 块前进一步
0.5 秒更新一次结果
```

一秒波形没有直接送进大模型。DSP 把它压缩成 64 维对数频带特征，并缩放到 0—100 的固定输入范围。分类器只有一层 32 神经元的 ReLU 隐层，结构为 64–32–5：

```text
64 维振动频带
        ↓
32 个 ReLU 隐藏神经元
        ↓
5 类得分与 Softmax 概率
```

这个选择很克制。频谱先提炼机械故障最有用的结构，神经网络只负责学习频带组合与故障类别之间的边界。模型小、内存行为可预测，也更适合持续运行在 MCU 上。

## 量化不是一句“转成 INT8”

训练完成后，模型参数被导出为 C 头文件，跟随固件一起编译进片上 Flash。设备启动时不需要查找模型文件，也不依赖 SD 卡和网络。

当前导出版本采用 Q7 权重、INT32 第一层累加和定点隐藏层，输出层缩放、偏置与 Softmax 仍保留浮点运算。因此准确说法是“静态 Q7 权重量化模型”，不是“全 INT8 网络”，更不是 Ethos-U55 加速版本。

按当前生成头文件实际计算，板载模型参数为 **2508 字节**。这个数字只代表模型参数，不包含 RT-Thread、界面、日志、缓冲区和其他固件代码。

### 当前机器可读指标

| 评估对象 | Accuracy | Macro-F1 | 说明 |
|---|---:|---:|---|
| FP32 留出记录测试 | 96.50% | 96.44% | 200 个测试窗口 |
| 动态 INT8 仿真 | 97.00% | 96.95% | 离线量化仿真 |
| 静态 Q7 板载导出 | 96.50% | 96.42% | 与当前固件参数对应 |

静态 Q7 导出与 FP32 的预测一致率为 99.5%。在 FP32 混淆矩阵中，四种故障类别的召回率均为 100%；七个正常窗口被判成不对中或不平衡。这个结果说明模型对已覆盖故障较敏感，同时也暴露了正常状态下的误报问题。

![FP32 留出记录测试集混淆矩阵](../artifacts/training/kaist-vibration-v1/confusion_matrix.png)

仓库早期训练报告曾把动态 INT8 的 97.00% 写到静态导出项，并把参数写成 2504 字节。比赛材料应以当前 `metrics.json` 和固件 `edgedoctor_onboard_model_bytes()` 的输出为准，使用上表口径。

## 97% 不是全部答案

普通测试集说明模型能否识别未见记录，LOLO 则检查它面对未见负载时会怎样。

| 留出的负载 | Accuracy | Macro-F1 |
|---|---:|---:|
| 0 Nm | 92.33% | 87.64% |
| 2 Nm | 93.50% | 90.44% |
| 4 Nm | 82.17% | 77.88% |

![量化结果与按负载留一验证](../artifacts/training/kaist-vibration-v1/generalization_quantization.png)

4 Nm 是最难的一折。Macro-F1 从普通留出测试的 96.44% 降到 77.88%，说明负载变化仍会明显影响特征分布。这个数字不应该藏进附录。它划出了系统当前的使用边界，也给下一步工作指出了方向：补充目标设备数据、覆盖更多负载、做域泛化和置信度校准。

所以，96.50% 代表 KAIST v6 振动记录和当前记录级划分下的结果，不代表所有设备、所有安装位置和所有负载下都能达到同样精度。真正部署到工厂前，仍要用目标设备的标注数据重新校准和验收。

## 模型进入 RTOS 之后

离线脚本跑通一次推理并不难。板端系统的难点在于：采样不能停，窗口不能乱，界面不能卡住 DSP，Flash 写日志也不能拖慢下一次诊断。

EdgeDoctor-RT 把这些工作拆开处理。

### 固定窗口，不在热路径申请内存

音频、振动块、分析窗口、频带特征和回放工作区都使用静态存储。20 ms 数据块进入固定环形窗口，系统同时检查帧号和时间戳连续性。遇到跳帧或时间倒退，窗口会重新预热，并累计不连续次数。采集、DSP 和推理热路径不做动态内存分配，避免堆碎片和不可预测的申请时间。

### UI 读快照，不占住推理

推理完成后，结果先发布到双缓冲快照。UI 读取已经完成的一份结果，不直接占用正在写入的数据。频谱数据也采用双缓冲更新。这样，即使页面刷新或触摸操作稍慢，也不会把显示延迟传回 DSP 热路径。

### 日志异步落盘

每次诊断结果被送入固定容量消息队列，由独立线程写入 `/flash/edgedoctor.csv`。队列满时系统记录丢弃数量，写入失败也有单独计数。日志工作不会同步阻塞推理线程，问题也不会被悄悄吞掉。

### 性能数据来自周期计数器

M55 运行时优先使用 DWT 周期计数器记录预处理、推理和端到端耗时，并保留 P50、P95、帧数、队列峰值和丢帧统计。若 DWT 不可用，才回退到系统时钟。`edgeai info` 可以从串口直接读出这些数据。

### 损坏输入直接拒绝

板端回放使用 EdgePack 格式。文件头包含采样率、通道数、样本数、负载、标签、载荷长度和 CRC32。解析器会检查版本、范围、长度以及载荷校验和。格式不匹配、长度异常或数据损坏时，文件不会进入推理链。

## HMI 不是装饰，是处置入口

800 × 480 的本地界面分成四页，每一页对应现场人员的一类问题。

| 页面 | 它回答的问题 |
|---|---|
| 概览 | 设备现在是否健康？系统是否在线？ |
| 信号 | 声音与振动频带最近发生了什么变化？ |
| 诊断 | 当前故障是什么？置信度和五类概率是多少？ |
| 系统 | 推理有多快？有没有丢帧？日志是否正常？ |

![HMI 中使用的设备概览素材](../firmware/m55/ui/edgedoctor_machine_preview.png)

严重报警出现时，系统可以跳转到诊断页。操作员看到故障类别、置信度和健康度后，可以执行“确认报警”。确认不会抹掉故障，而是留下“报警已被现场人员接收”的状态。诊断结果随后进入 CSV 日志，形成从发现、判断到处置、追溯的完整链条。

当前 HMI 既能显示运行时真实快照，也提供固定演示数据。两者用途不同：真实快照用于模型回放和系统验证；`edgeui demo on` 与 `edgeui alarm` 用于稳定展示页面和报警交互。比赛中必须把后者称为“报警交互演示模式”。

## 现场演示怎么走

现场最好准备两条路线。

第一条是稳定的 HMI 报警演示，确保评委能完整看到交互：

```text
edgeui demo on
edgeui tab 0
edgeui tab 1
edgeui alarm
edgeui ack
edgeui tab 3
edgeui clear
edgeai info
```

讲解顺序可以这样安排：

1. 在概览页介绍健康度、板载模型和 Flash 日志状态。
2. 切到信号页，说明频带数据如何随时间更新。
3. 执行 `edgeui alarm`，明确告诉评委这是报警交互演示。
4. 展示诊断页中的轴承外圈故障、92% 置信度和降到 13 的健康度。
5. 点击“确认报警”，解释确认状态与故障状态的区别。
6. 切到系统页，查看 DSP 耗时、队列、丢帧和日志统计。
7. 执行 `edgeai info`，从串口核对模型名、参数字节数、存储位置和运行统计。

第二条是真实振动样本回放。将准备好的 `.edgp` 文件放入板端 Flash 后执行：

```text
edgeai replay /flash/<sample>.edgp
edgeai info
```

这条路线用来证明数据确实经过板端 DSP 和模型。比赛前应至少准备一个正常样本和一个故障样本，并提前核对预测、日志行数和页面变化。若现场硬件或投屏出问题，再切换到 60 秒备用视频。

“EdgeDoctor-RT 没有把目标定成一张更漂亮的准确率表。我们保留了记录级划分，公开了 4 Nm 下的性能下降，也因为原始声学与振动不同步而放弃了虚假的多模态成绩。它现在已经把可信数据、轻量模型、实时运行和报警留痕放进同一套系统。工业诊断不一定依赖云服务器和大型模型，一块边缘芯片也可以成为设备旁边持续工作的医生。”

## 评委追问时，直接这样回答

### 为什么不用更大的网络？

频带特征已经把一秒波形压缩成 64 个与机械状态相关的量。当前任务不需要用大网络重新学习全部时域结构。小模型带来的好处很直接：参数少、内存固定、执行路径短，也更容易核对离线与板端的一致性。

### 96.50% 会不会是数据泄漏？

划分单位是完整记录，不是窗口。记录 ID 在切窗之前分开，同一条原始记录不会同时进入训练和测试。仓库保存了划分清单和机器可读指标，可以复查。

### 为什么量化后有一项反而更高？

97.00% 对应动态 INT8 离线仿真，不是当前静态板载导出的成绩。量化会改变少量决策边界，在有限测试集上可能碰巧修正个别样本。当前板载静态 Q7 导出为 96.50%，与 FP32 预测一致率 99.5%。

### 2508 字节是不是整个程序？

不是。2508 字节只计算模型参数。完整系统还包括固件代码、RT-Thread、LVGL、窗口缓冲、线程栈和日志队列。

### 已经使用 Ethos-U55 了吗？

没有。当前是 M55 上的 Reference C 实现，使用 Q7 权重和部分定点计算。Ethos-U55 与 CMSIS-NN 属于后续加速方向，只有拿到编译覆盖率、板端一致性和实测时延后才会对外宣称。

### 为什么界面有声音频带，模型却只用振动？

系统数据通道和界面为声振融合预留了位置，但 KAIST 公开声学文件与振动文件不是真正同步采集。为保证成绩可信，当前分类函数只读取振动特征。声音频带可以用于界面与后续采集验证，不能算进当前五分类精度。

### 4 Nm 为什么下降明显？

负载变化改变了振动分布。4 Nm 留一折的 Macro-F1 为 77.88%，说明当前特征和模型对高负载工况仍敏感。项目没有把这项结果平均掉；后续会增加目标工况数据、域泛化训练和置信度校准。

### 板端时延和稳定性已经正式验收了吗？

还没有完成正式验收。仓库中的短时 smoke 回放只能证明链路可运行，不能代替至少 200 个热样本的性能统计和 30 分钟连续回放。正式结果应包含 P50、P95、丢帧、日志数量、内存变化和串口原始记录。

## 比赛前只补证据，不再堆功能

项目主线已经完整。比赛前最有价值的工作，是把板端证据补齐：

- 拍摄概览、信号、诊断、系统四个页面的实机照片；
- 准备正常与故障振动样本的板端回放；
- 保存 `edgeai info` 的完整串口输出；
- 连续回放 30 分钟，记录 P50、P95、丢帧、日志数量和内存变化；
- 完成至少 100 次页面切换与触摸响应测试；
- 录制一段 60 秒备用演示视频；
- 统一修正旧材料里的“2504 B”和“静态 INT8 97.00%”口径；
- 不宣称 Ethos-U55 已启用，不把演示报警说成真实传感器推理；
- 把“声振融合”写在路线图，把“振动五分类”写在当前成果里。

## 最后一句

EdgeDoctor-RT 的价值，不在于把一个模型塞进开发板，而在于让设备的细微振动能在现场变成一次及时、可信、留得下记录的判断。
